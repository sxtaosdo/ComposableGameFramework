# 全项目目录与美术资产维护规范

状态: Accepted

Owner 确认日期：2026-09-17。范围修正：按后续明确要求适用于所有项目。

本文是 shidai3 项目目录与美术资产维护的权威正文，由 P0002 维护。父仓 `AGENTS.md`、`AI_CONTEXT.md` 及各项目入口只引用本文，不复制第二份完整合同。

> 规范已确认不等于存量项目已经完成迁移。实际交付、迁移和验证状态须分别记录，不得由本文状态推断。存量项目的合规状态以各自迁移记录为准。

## 1. 适用范围与权威关系

本规范适用于 shidai3 管理的**所有项目**，不限定 cook、P4000、Cocos 或游戏项目。包括游戏产品、框架、开发工具、流程实现，以及 IP／美术／内容／文档项目；新建项目和存量项目均适用。各项目保留 Owner 指定的技术栈，不因本规范切换引擎。

“项目根目录”由该项目既有 README／合同确定；独立仓库、submodule 也不能因 Agent 只打开子仓就绕过规则。父仓与聚合目录中已有的治理、导航、设计文档职责保持不变，不把其中所有内容强塞进 art 或 tests。存量结构并非新增权限，实际不合规项按各项目迁移记录逐一处理。

规则按用途适用：没有美术生产需求的工具无需创建空 art；没有测试内容的纯文档项目不创建空 tests。所有项目仍须遵守“不随意新增一级目录”。P8000 工具项目自身的工具源码属于该产品代码，不再递归搬往另一个 P8000 项目。

统一技术规范由 P0002 维护；工作区根 AGENTS、AI_CONTEXT 和各项目入口按需引用同一权威正文，不能只挂到 P4000 下。既有 product-project-layout.md 若已经落库，须明确替换或设置短迁移入口，不能让旧限定范围与新正文并存为双权威。

本文负责目录技术合同；Git / 版本规则以同目录 `git.md` 为准，Agent 执行与交付流程仍由父仓及 P0003 负责。README、AGENTS、Skill 入口只引用本文，不复制第二份完整合同。

## 2. 项目根目录：白名单与申请

人工维护的新增一级业务目录只允许 `art/` 和 `tests/`。项目所用引擎／技术栈的标准工程结构、必要自动生成目录，以及 Git 必需的标准机制按既有工程合同使用；不能把任何工具输出都称为“自动生成”来获得豁免。

Cocos 项目的 `assets/` 继续承载运行资源；Godot、Unity、Web、CLI、后端与工具项目维持各自既有 Accepted 工程结构，不能强制套用 Cocos 的 assets。既有 `settings/`、`extensions/` 等引擎工程路径按本项目实际合同维护，不借治理任务改写或搬动其内容。新增标准路径须有适用引擎版本或已接受工程合同依据；不能只凭其他项目存在同名目录来认定。

除上述已批准业务目录及有依据的标准工程／自动生成目录外，不得自行新建一级目录，包括 `scripts/`、`tools/`、`temp/`、`output/`、`generated/`、`backup/`、`docs2/` 等。这里禁止的是自建业务或工具目录；引擎确实生成同名标准目录时，仍按其真实生成来源判断。

确实需要新的一级目录时，须先向 Owner 说明准确路径、职责、现有目录为什么不足、维护及清理责任，获得明确批准后才可创建。批准一个具体路径不等于批准所有同名目录。

根目录既有 README、AGENTS、配置、版本及日志等文件不属于“新增目录”，但仍须满足文件职责、命名和变更范围要求。

存量目录不因存在而成为永久白名单，也不能因不在白名单就立即删除。须登记迁移处置，迁移前禁止继续往非合规目录扩展无关内容。特别是已有提交 Hook、依赖与构建入口，必须先迁移引用并验证，再移除旧路径。

## 3. 根目录内外的职责划分

| 内容 | 位置 | 边界 |
|---|---|---|
| 项目专属美术生产资源 | `art/` | 参考资料、效果图、生成和加工过程、确认后的美术源资产 |
| 正式运行资源与项目产品代码 | 适用引擎／技术栈的既有合法结构，Cocos 示例为 `assets/` | 不为统一到 art 而破坏资源引用、构建或打包 |
| 项目测试 | `tests/` | 单元、集成、端到端测试及项目专属测试数据和辅助代码 |
| 通用开发工具 | `P8000/<tool>/` 独立工具工程 | 切图、图片处理、资源分析、通用截图、批处理等实现不进入产品目录 |
| 产品不可分割的工程适配 | 产品既有合法结构或必要根文件 | 仅限自身运行、构建、数据生成、发布所必需的代码；不因此自动批准 `scripts/` |

工具的运行输入、输出、项目配置与工具实现必须分开：例如切图实现属于 P8000，cook 的输入图和切图结果属于 cook/art。

项目专属测试辅助代码允许位于 `tests/helpers/`。真正跨项目的测试工具与其自身测试归所属 P8000 工具工程，不应在每个游戏重复维护。

工具外移后仍需保证产品可按文档独立安装依赖和验证。禁止只把命令改成依赖某个人机器上恰好存在的 `../../P8000/...`，并以此声称完成迁移。

## 4. art 的固定结构

`art/` 只允许以下三个一级子目录及维护入口：

```text
art/
├── README.md
├── manifest.csv
├── reference/
│   └── <模块>/
├── work/
│   └── <模块>/
│       ├── r01/
│       │   ├── generated/
│       │   ├── sliced/
│       │   └── README.md
│       └── r02/
└── final/
    └── <模块>/
```

不得再于 art 根级新增 `ui/`、日期批次目录、`source/`、`designs/`、`candidates/`、`temp/`、`output/`、`new/`、`backup/` 等平行目录。已有同类目录列入迁移清单，不直接删除。

`home`、`gameplay`、`loading`、`common` 等模块名可按实际内容增加，不需逐次申请；模块以下按职责组织。内部自治不允许藏入工具源码、另建一套平行资产库，或绕过根级目录限制。

`README.md` 维护当前模块、维护入口、进行中的轮次、已知迁移项及保留／清理说明。`manifest.csv` 维护正式资产和关键资源的当前选择及来源关系。

## 5. 参考、轮次、最终源资产与运行资源

资源流向为：

```text
reference → work/<模块>/rNN → final/<模块> → 适用工程的运行资源目录（Cocos 为 assets）
```

### 5.1 reference：参考资料

只保留确实在使用或有明确保留理由的参考资料，记录来源、用途及已知使用限制。共享 IP 资料优先引用已有权威入口，不无理由复制整套共享资源。

来源不明须如实标记，不根据文件名编造作者、授权、生成模型或取得时间。

### 5.2 work：生成与加工轮次

每个模块独立维护递增轮次编号 `r01`、`r02` 等。删除旧轮次后不复用旧编号；下一轮编号及历史概要在 art/README 或轮次说明中记录。

`generated/` 保存本轮完整生成图；`sliced/` 保存与明确原图对应的切图。原图已经被切图、被选中或作为下轮输入后，不通过覆盖它来冒充同一版，改用新候选编号或新轮次。

同轮存在多个完整候选图时，使用清晰编号并把切图按来源分开，例如：

```text
work/home/r03/
├── generated/
│   ├── design-01.png
│   └── design-02.png
├── sliced/
│   ├── design-01/
│   │   └── start-button.png
│   └── design-02/
│       └── start-button.png
├── preview.png
├── comparison.png
└── README.md
```

`preview.png`、`comparison.png` 是存在实际取证时才保存的还原截图和对比图，不是必填占位图片。放在对应轮次内，不为它们新建 art 根级的截图或比较目录。

禁止使用 `button_new.png`、`button_final2.png`、`最终版3.png` 等含混命名承担版本身份。轮次、候选编号和用途共同确定来源，不仅依赖“同一个文件夹”。

轮次 README 保持简短，但应能说明：目的、父轮次、生成或加工方式、各候选和切图来源、选择结果、失败原因、是否继续使用以及保留／清理理由。无法追溯的旧资料标记“来源待核对”，不得伪造轮次对应关系。

### 5.3 final：已确认的美术源资产

只有经过该项目现有确认流程选中的源资产才进入 `final/`。本次目录规则确认不代表任何现有图片已经获准使用。

不同资源可以来自不同轮次；不能因为首页背景采用 r03，就把 r03 的所有按钮和图标一并认定为已采用。manifest 必须能逐项回答当前背景、按钮和图标分别采用何处内容。

`final/` 不保留一串 `final2`、`latest`、`backup` 版本目录；使用稳定资产名并保留来源记录。正式资产替换时同步更新清单和实际使用去向，不通过移动文件自动宣告已在游戏生效。

### 5.4 引擎／工程运行资产（Cocos 示例为 assets）

`final/` 不是 `assets/` 的全量镜像。final 保存必要的源图、确认源素材；assets 保存实际运行所需资源及其工程引用，两者可能存在尺寸、压缩、图集等差异。

Cocos 项目不得为了目录整理直接编辑 `.scene`、`.prefab`、`.meta`。涉及运行资源移动或引用变更时，须由绑定本项目的 Creator / MCP 完成序列化并进行相应验证。

## 6. 持久记录与来源完整性

manifest 只登记正式资产和关键资源，不要求给每一个短期实验文件建一行；实验文件由所在轮次的 README 成组说明。不能因此保留无人解释的大量实验文件。

建议最小字段如下，允许按实际需求扩展字段，不另建第二份权威清单：

```csv
资产ID,模块,状态,最终源路径,来源轮次,来源文件,历史来源定位,运行资源路径,来源或生成方式,保留或清理说明,更新日期
```

工作文件仍保留时，“来源文件”指向当前有效路径。来源轮次从工作树清理后，“历史来源定位”须能指向已保存的真实仓库提交及原路径，或已有且可读取的存档；不得留下无法解释的失效来源链接。

不得编造历史提交、文件哈希、确认人、确认日期或运行资源去向。不知道的内容明确标记待核对；不能仅依据图片看起来相似就补齐来源。

art/README 与 manifest 中的状态必须反映事实，区分候选、已确认源资产和已经接入游戏；存放进 final 不等于已经完成 Creator 导入和运行验证。

## 7. 清理与保留

每轮结束、正式资产替换及阶段收尾时检查无用资源。已废弃且无引用、无保留理由的生成图、切图和中间文件应从当前工作树删除；不永久保存所有轮次。

保留有复用或诊断价值的失败轮次时，记录具体理由及复查时点，不以“可能以后有用”长期堆积。

清理前须确认不再被当前工作、下一轮生成、final 或运行资源使用；来源追溯记录须仍成立。对用途、引用或保存状态不能确认的文件，不自动删除。

Git 仅能恢复已真实提交且历史仍保留的内容，不能恢复从未提交的文件；采用 LFS 或外部存档的资料，还须确保对应对象实际可取得。不得把“用了 Git”视为所有资源已备份。

本规范的日常清理不包含重写 Git 历史、删除远端 LFS 对象或清理共享存储。此类动作须按独立任务授权和执行。

## 8. tests 的组织

统一使用项目根 `tests/`，不并存另一套 `test/`。按实际测试需要使用：

```text
tests/
├── README.md
├── unit/
├── integration/
├── e2e/
├── fixtures/
└── helpers/
```

这些子目录按需创建，不为模板填满无内容目录。测试代码、项目专属 fixture 和测试 helper 不进入美术目录；测试实际使用的最小美术样本可作为 fixture 保存并说明来源，不复制整个 art 库。

## 9. 迁移与验收

先核对目标仓库、分支、工作树脏改动和已有规范。建立旧路径→新路径→来源／用途→引用变更→验证结果的映射，再执行迁移。先处理可证明的归类，不把日期或 `v2` 字样直接当作真实生成轮次。

通用工具迁移须同步命令、依赖、Hook、配置和使用说明；新入口经验证可用后才能移除旧入口。目录规则不得成为绕过版本门或导致产品无法独立验证的理由。

完成状态分开报告：规范落库、执行入口接入、资产清单完成、素材迁移、工具迁移、测试迁移、适用验证及 Git 交付。未执行或未验证的项不得标为完成。

本规范不额外引入强制 GPT 审查、复杂审批系统或独立的回执框架。是否需要新增工具实现按实际任务确定，工具代码遵守 P8000 边界。
